# OpenClaw deployment policy

Статус: принято для текущей установки

## Цель

Зафиксировать правила сопровождения рабочей Docker-установки OpenClaw так, чтобы:
- избежать внезапных поломок из-за неявных обновлений;
- сохранить совместимость с `clawdock`;
- локализовать наши доработки;
- упростить обновление, откат и дальнейшее сопровождение.

---

## 1. Базовая модель репозитория

Текущая установка должна оставаться совместимой с ожиданиями `clawdock`.

`clawdock` ожидает наличие файлов:
- `${CLAWDOCK_DIR}/docker-compose.yml`
- `${CLAWDOCK_DIR}/docker-compose.extra.yml`

Поэтому рабочий каталог OpenClaw хранится в структуре upstream-репозитория OpenClaw.

### Принятое решение

Для сопровождения использовать **fork OpenClaw**, а не отдельный deployment-репозиторий.

### Причина

Отдельный `openclaw-deploy`-репозиторий в текущей схеме создаст лишнюю обвязку:
- симлинки;
- копирование файлов;
- wrapper-скрипты;
- дополнительную хрупкость.

Это ухудшает понятность и аварийную сопровождаемость.

### Правило

Рабочий каталог должен быть:
- совместим с `clawdock`;
- основан на fork OpenClaw;
- подключён к официальному upstream как дополнительный remote.

---

## 2. Git-модель

### Remotes

- `origin` — наш fork OpenClaw
- `upstream` — официальный репозиторий OpenClaw

### Правила

1. Локальные рабочие изменения коммитятся в наш fork.
2. Обновления OpenClaw подтягиваются из `upstream` осознанно и отдельно.
3. Нельзя рассматривать случайный `git pull` с плавающей базы как допустимый способ обновления рабочей установки.

### Предпочтительный порядок обновления

1. Создать отдельную ветку обновления.
2. Подтянуть нужные изменения из `upstream`.
3. Адаптировать локальные доработки при необходимости.
4. Собрать образ.
5. Пройти smoke-check.
6. Только после этого вносить обновление в рабочую ветку.

---

## 3. Правила для docker-compose файлов

### `docker-compose.yml`

Это **ванильный upstream-файл**.

#### Правило

По возможности не изменять `docker-compose.yml`.

Если требуется локальная доработка, приоритет такой:
1. решить через `.env`;
2. решить через `docker-compose.extra.yml`;
3. решить через `Dockerfile.custom`;
4. и только в крайнем случае менять upstream `docker-compose.yml`.

### `docker-compose.extra.yml`

Это основной файл для наших локальных доработок.

В нём допустимо хранить:
- дополнительные environment variables;
- дополнительные volumes;
- подключение `docker.sock`;
- соседние сервисы, завязанные на OpenClaw;
- иные локальные override-настройки.

#### Правило

Все эксплуатационные доработки по compose по умолчанию вносятся именно в `docker-compose.extra.yml`.

---

## 4. Правила для Dockerfile.custom

`Dockerfile.custom` — единственное штатное место для локального расширения базового образа OpenClaw.

### Базовый образ

#### Правило

Базовый образ OpenClaw всегда должен быть pinned на конкретную версию.

Запрещено использовать в рабочей системе:
- `:main`
- иные плавающие теги без отдельного осознанного решения.

### Текущая базовая версия

Текущая целевая база:
- `ghcr.io/openclaw/openclaw:2026.3.13-1`

### Обновление базовой версии

Обновление версии выполняется только как отдельная задача:
1. выбрать новую версию;
2. изменить pin в Dockerfile;
3. пересобрать образ;
4. пройти проверку;
5. при успехе зафиксировать изменение в git.

---

## 5. Правила построения Dockerfile.custom

### Общий принцип

Новые локальные компоненты добавляются так, чтобы максимально использовать Docker layer cache.

### Правило

Каждый **логический компонент** или группа тесно связанных операций должен добавляться отдельным `RUN`-слоем.

### Уточнение

Для `apt`-слоёв операции:
- `apt-get update`
- `apt-get install`
- cleanup

должны находиться в **одном и том же `RUN`**, чтобы не использовать устаревший индекс пакетов.

### Дополнительные правила

1. Новые компоненты по возможности добавлять новыми слоями, а не переписывать старые без необходимости.
2. Тяжёлые и редко меняющиеся зависимости ставить раньше.
3. Более изменчивые доработки — ближе к концу Dockerfile.
4. `Dockerfile.custom` должен оставаться читаемым и объяснимым.

---

## 6. Именование и воспроизводимость образов

### Правило

Локальный образ должен быть явно отделён от upstream-образа по имени или тегу.

Желательно использовать наименования, из которых видно:
- от какой версии OpenClaw он построен;
- что это локальная кастомная сборка.

Примеры допустимого стиля:
- `openclaw:2026.3.13-1-local`
- `openclaw-custom:2026.3.13-1-r1`

Если по operational-причинам используется имя вроде `openclaw:local-custom`, базовая версия должна быть явно указана в `Dockerfile.custom` и задокументирована.

---

## 7. Секреты и переменные окружения

### Правило

Секреты не должны храниться в git.

В репозитории допустимо хранить:
- `.env.example`
- документацию по обязательным переменным

В git не должны попадать:
- реальные токены;
- реальные пароли;
- рабочие API keys;
- иные чувствительные секреты.

---

## 8. Правила обновления

Обновление OpenClaw, базового образа или локального образа — это отдельная эксплуатационная процедура, а не побочный эффект обычной работы.

### Перед обновлением

Нужно зафиксировать:
- текущую рабочую версию базового образа;
- текущий локальный тег образа;
- текущее состояние локальных доработок.

### После обновления

Нужно выполнить smoke-check.

Минимальный smoke-check:
1. контейнеры поднимаются;
2. healthcheck успешен;
3. control UI доступен;
4. CLI-команды не ломаются на загрузке критичных plugins;
5. telegram bindings работают;
6. hooks и связанные сервисы работают;
7. критичные агенты отвечают.

Только после этого обновление считается принятым.

---

## 9. Правила отката

Для каждого заметного обновления должен существовать понятный путь отката.

### Минимум, который нужно знать заранее

- какой образ был предыдущим рабочим;
- какой commit был предыдущим рабочим;
- как вернуть compose и образ;
- как проверить, что откат успешен.

Откат должен быть:
- коротким;
- воспроизводимым;
- не зависящим от памяти оператора.

---

## 10. Границы локальных доработок

Локальные изменения должны быть минимальными и локализованными.

### Предпочтительный порядок внесения изменений

1. `.env`
2. `docker-compose.extra.yml`
3. `Dockerfile.custom`
4. документация в `ops/`
5. только потом — изменения upstream-файлов или кода OpenClaw

### Смысл

Чем дальше изменение от upstream-кода, тем проще:
- обновляться;
- разбираться после паузы;
- откатываться;
- диагностировать неисправности.

---

## 11. Что считается нормой для этой установки

Для текущей установки нормой считаются:
- ванильный `docker-compose.yml` из OpenClaw;
- локальный `docker-compose.extra.yml` рядом с ним;
- локальный `Dockerfile.custom` рядом с ним;
- сопровождение через fork OpenClaw;
- controlled upgrades вместо плавающей базы;
- явная документация operational-решений.

---

## 12. Первое практическое следствие этого policy

Текущая проблема с telegram plugin рассматривается как следствие недостаточно контролируемой базовой версии образа.

Первое исправление должно идти в логике этого policy:
1. уйти с `main`;
2. зафиксировать базовую версию;
3. привести `Dockerfile.custom` к слоистой и сопровождаемой структуре;
4. только потом продолжать диагностику и стабилизацию runtime.
